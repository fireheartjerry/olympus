# Roadmap and Release Train

## 1. Release doctrine

Fire advances through **earned capability**, not feature accumulation. Every release must establish one new end-to-end behavior through the existing authority, Temporal, node, audit, cost, freeze, revocation, recovery, and evidence paths.

A release is not complete because code exists. Each item has five distinct states:

1. specified;
2. implemented;
3. enabled in the control-plane catalog;
4. granted to a live embodiment;
5. verified under normal and failure conditions.

The program ledger must report those states separately. This prevents source code from becoming a fictional production deployment through the ancient engineering technique of optimistic wording.

## 2. Release trains

### R0 — Governed distributed substrate

**Status:** substantially achieved in the inspected baseline.

Scope:

- WebAuthn-backed authority;
- PostgreSQL and Temporal durability;
- outbound-only Windows node;
- freeze, revocation, restart recovery, and evidence;
- scoped file primitives in source;
- off-host audit and Temporal recovery work.

Exit evidence:

- production workflow receipt;
- recovery drills;
- audit-chain verification;
- exact live-grant inventory.

### R1 — Canonical cognitive contracts

**Package contribution:** implemented as the side-effect-free overlay in this ZIP.

Scope:

- objective contracts;
- goal graph;
- Jerry-model snapshots and update proposals;
- selective-memory contracts;
- persona and identity lineage;
- takeover session semantics;
- self-improvement promotion decisions;
- evaluation metrics.

Exit criteria:

- contracts merge without changing live behavior;
- generated JSON Schemas are reproducible;
- focused tests and full repository gates pass;
- no production state or capability is mutated.

### R2 — Objective runtime foundation

Scope:

- durable objective-contract tables;
- objective creation through the production authority surface;
- canonical digest and audit event;
- Temporal no-op objective workflow;
- inspect/cancel/freeze/status operator surfaces;
- objective recovery after OVH restart.

Exit criteria:

- one authorized objective survives restart;
- no-op execution emits typed evidence and zero cost;
- duplicate submission is idempotent;
- stale or expired authority fails closed.

### R3 — Fire Operator v1

Scope:

- reconcile catalog capability versus live grants;
- process inspection;
- window inventory;
- allowlisted application launch;
- scoped project discovery through file list/read;
- one isolated Codex or Claude worktree flow;
- phone/Discord initiation and evidence delivery.

Representative objective:

> Open the active project environment, inspect the repository, run the approved coding worker on a bounded task, verify its changes, and report the result.

Exit criteria:

- one phone-to-Windows useful workflow;
- no arbitrary command string or unrestricted path;
- live freeze, revocation, duplicate-delivery, node-loss, and restart tests;
- exact cost and evidence receipts.

### R4 — Browser and workspace operation

Scope:

- governed isolated browser sessions;
- Chrome/Playwright/CDP capability adapter;
- authenticated-profile separation;
- GitHub, Gmail, Calendar, and Drive adapters;
- prompt-injection taint propagation;
- reversible external-effect reconciliation.

Exit criteria:

- browse, inspect, and complete one bounded external workflow;
- no page content can authorize a tool call;
- screenshots, API receipts, and state reconciliation agree.

### R5 — Takeover v1

Scope:

- active-context capture;
- objective inference with confidence;
- brief interpretation confirmation only when material ambiguity exists;
- orchestration across file, app, browser, and coding capabilities;
- manual-resume and stop semantics;
- live operator observation.

Exit criteria:

- “Fire, take over” completes representative coding and presentation tasks;
- no unrestricted `desktop.takeover@1` primitive is required;
- takeover is interruptible, evidence-backed, and recoverable.

### R6 — Memory and world model v1

Scope:

- event ingestion from approved digital streams;
- bounded raw buffers;
- semantic event extraction;
- memory candidates, promotion, contradiction, and provenance;
- project/world entity graph;
- retention and deletion policy.

Exit criteria:

- Fire reconstructs an active project state after restart;
- retained facts are source-linked and challengeable;
- raw media retention stays bounded and observable.

### R7 — Jerry Cognitive Model v1

Scope:

- explicit top-level goal graph;
- preference hypotheses;
- observed versus reflective Jerry predictions;
- domain communication profiles;
- corrections and learning directives;
- deep forensic explanations;
- offline replay evaluation.

Exit criteria:

- held-out preference and decision benchmark;
- Jerry approves the reasoning, not merely the answer;
- model updates remain proposals until verified and promoted.

### R8 — Proactive stewardship v1

Scope:

- standing objectives;
- daily planning cycle;
- opportunity and risk detection;
- self-maintained backlog;
- silent reversible work;
- bounded notification policy;
- multi-day objective continuation.

Exit criteria:

- Fire completes useful work without a direct command;
- alert precision is high enough to avoid notification sludge;
- every initiated task traces to an objective and authority basis.

### R9 — Social representation v1

Scope:

- conversation delegation;
- per-person communication profiles;
- negotiation and low-risk commitments;
- conversation summaries;
- internal provenance distinguishing Jerry-authored, Jerry-delegated, and Fire-predicted communication.

Exit criteria:

- representative conversations satisfy Jerry on content, tone, and commitments;
- no fabricated direct experience;
- commitments are surfaced according to policy.

### R10 — Governed self-improvement

Scope:

- improvement proposal generation;
- shadow evaluation;
- independent verifier;
- canary, rollback, and succession lineage;
- competing implementations;
- progressive promotion authority.

Exit criteria:

- Fire improves one subsystem and safely rolls it back under induced regression;
- constitution, authority, and identity changes remain owner-gated.

### R11 — Elastic execution mesh

Scope:

- external CPU/GPU workers;
- queue and placement policy;
- workload-specific autoscaling;
- cost governor and orphan cleanup;
- provider portability.

Entry gate:

- measured local/OVH saturation, isolation requirement, or hardware need.

Kubernetes remains optional. It is a scheduler, not a rite of passage.

### R12 — Long-term continuity and stewardship

Scope:

- extended unavailability charter;
- trusted-family authority;
- financial and operational continuity;
- multi-year memory maintenance;
- model and infrastructure succession.

Exit criteria:

- progressively longer simulation drills;
- explicit legal and financial boundaries;
- owner recovery remains independent of Fire's ordinary runtime.

## 3. Program cadence

Use two nested cadences:

- **Capability slices:** days to a few weeks, one narrow end-to-end behavior.
- **Release trains:** several slices, one coherent user-facing capability.

Every slice closes with:

1. current-state diff;
2. threat-model delta;
3. unit and integration evidence;
4. live or deliberately non-live status;
5. cost delta;
6. rollback procedure;
7. next bottleneck.
